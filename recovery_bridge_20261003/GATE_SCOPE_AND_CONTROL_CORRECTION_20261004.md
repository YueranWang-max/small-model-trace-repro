# 源任务门槛的适用范围与下一阶段对照纠正

## 重要方法检查

重新查阅Zou与Tang原论文第4.3节，发现不能把我们设定的源任务F1>=.70、EM>=.50视为Trace as State的必要条件。原文GraphWalks 256K的首次作答F1约36.4%(BFS)、46.5%(parents)，EM约31.6%和29.2%，仍观察到明显轨迹复用收益。若用我们的性能门槛决定“是否允许检验轨迹”，原论文自己的有效条件也会被筛掉。

来源：[原论文第4.3节及表3](https://arxiv.org/html/2609.02702)。这是对表中数值与本地门槛的比较，不是对小模型收益的证明。

## 保持冻结门槛，纠正其解释

- 当前混合模型源资格实验继续按冻结方案完成，不改门槛、不删失败、不把未通过改称通过。此前8B门槛失败与缺失结果也保持原结论。
- 这个门槛是本地设定的源任务表现/部署决策门槛，不是原论文的定理假设，也不是判定该模型“不能接受轨迹复用检验”的充分证据。
- 输入长度、模型身份、请求配置、原始输出与成本账本的资格核验必须通过或明确报告失败。它们与源任务F1/EM是否高于性能门槛是不同要求。
- 源任务较弱但输入与原始轨迹可核验时，仍可冻结一个独立的新题机制实验，检验轨迹是否救回失败。该阶段应叫机制验证/迁移实验，不能借此宣称源资格门槛通过或部署已经可靠。
- 高源任务分数也不能自动证明值得复用轨迹：接近满分的基线可能缺少提升空间，而产生五条轨迹仍有成本。

## 对照的名称与实现必须区分

原文的控制是：

| 条件 | 输入顺序 | 含义 |
|---|---|---|
| First pass | [x,q] | 一次原文与问题 |
| Question First | [q,x,q] | 题目提前，再在末端保留题目 |
| Re2 | [x,q,x,q] | 同一请求内重复完整原文与问题 |
| Trace prefix | [T,x,q] | 轨迹在原文前，末端题目 |
| Trace append | [x,T,q] | 同一轨迹在原文后，末端题目 |

原文表3中的Re2是完整上下文在同一请求内重复；不能把另一次独立发送[x,q]的调用称为这个Re2。原文控制名称是Question First，先前草稿使用的泛称question feedback需要明确对应这个形式，避免与Answer Feedback混淆。

我们已有五轨迹脚本的reread条件是新的[x,q]采样，使用与轨迹读出相同的预算/种子，作用是控制再次生成和较大读出预算；它不是同请求双上下文的Re2。pre/post脚本将同一个Operation尾部放在末端，已核对没有题目位置混淆。历史原始脚本和分数保持不变，报告只需明确控制的实际形式。

## 下一阶段应回答的问题

先判断前置/后置同一轨迹的效应，再比较前置轨迹与新的[x,q]读出、Question First及Re2。所有臂使用同一模型、完整原文、末端问题、相同读出预算和种子，不按源作答成功挑图。错误来源轨迹保留；可核验的程序Majority@5可作为五次来源调用的额外基线，Oracle@5仅为特权诊断。

准确率提升、轨迹顺序效应、输出可靠性和完整成本各自判断。即使顺序效应成立，也不能把更昂贵的准确率改善称为成本降低；即使源性能门槛失败，也不能据此断言原论文机制无效。

这是下一次实验冻结前的方法决策记录，不是对活跃源资格协议的改写，也不是确认了新的正面结果。样本数量、资源预算及统计比较仍需在首个新调用前固定。
