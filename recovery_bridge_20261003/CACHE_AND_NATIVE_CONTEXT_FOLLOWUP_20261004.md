# 后续值得检验的线索：实际缓存与模型原生窗口

状态：当前短状态实验继续按冻结方案运行。以下是后续研究笔记，不改变其预算、窗口、精度、样本或判定门槛，也不证明有性能提升。

## 逻辑token账单与实际计算必须区分

五来源单次成本证书针对API报告的完整输入输出token。相同原文若在服务层命中缓存，输入仍可能作为完整长度报告，但部分计算可以复用；这不能反过来删掉原来的token账单，也不能据账单界限否定实际延迟改善。SSR的前缀缓存/尾部复用先例已在PRIMARY_LITERATURE笔记中记录，此处不是新颖性主张。

本轮私有服务日志实际记录了prompt-cache状态、更新和cached n_tokens，已另存只读诊断owned_cache_diagnostic_20261004.json。某个日志片段的缓存状态为3个prompts、2772.803 MiB、限制8192 MiB；这是日志缓存容量指标，不是GPU驻留量或进程RAM实测。出现缓存事件不能证明每个读者复用了多少源计算，更不能由随机交错的研究调用拼出独占硬件连续部署耗时。

若后续专门研究延迟，应以完整单次部署为计时单位，让每个来源后紧接其自身读者，记录预处理、生成、缓存恢复、输入处理、输出生成、失败及总流程。对照亦需固定冷/热权重及缓存条件。当前七臂随机交错可用于本轮固定token预算比较，但不是缓存因果实验。全部所需来源生成支出仍计入，不按多个研究读者摊薄。

## 更大的原生窗口可能补齐原始迁移，而非解决token成本下界

此前首图五T联合输入144677token，在131072窗口里输入本身已不合规；加共同输出32768与64余量需177509。这个数在名义262144窗口内，说明过去的窗口失败是特定配置边界。Ollama的[Qwen3.5模型页](https://ollama.com/library/qwen3.5)列出256K上下文，已归档官方模型配置同样支持这一原生长度；它不保证本机内存足够或任务质量。

可以后续核验更长窗口与KV精度选择，使原始五轨迹质量实验实际可执行。Ollama[官方FAQ](https://docs.ollama.com/faq)说明KV量化依赖Flash Attention，默认f16，q8_0大致将KV部分内存减半，且质量影响取决于模型与任务。这里减半的是KV部分，不能把全部模型/工作区/循环状态/缓存内存都除以二。需在本机检验真正生效的类型、全GPU/CPU分配、输入计数、完整大输入和正常结束，再做质量比较。

当前只读启动日志显示flash_attn=auto、Flash Attention enabled及CUDA0 KV buffer2048 MiB；启动环境字段FLASH_ATTENTION=false不等于后端实际禁用。诊断保存的环境字段不得冒充内核是否启用的证明。当前实验不更改这些设置。

仓库里[Qwen3.5早期缓存移除问题](https://github.com/ollama/ollama/issues/14939)记录过上下文移动后重处理，现为Closed；不能据旧版本报告断言本轮0.35.1行为相同。[量化KV与工具调用问题](https://github.com/ollama/ollama/issues/17347)报告针对0.31.1、AMD/ROCm，不是本机NVIDIA/CUDA证据。这些材料支持把后端实现作为资格核验项，而非证明q8必然成功或失败。尝试读取0.35.1的两个具体Go源码URL未成功，尚不能据未读取的版本源码解释机制。

即使扩大窗口或节省KV内存成功，五完整来源的单次逻辑token下界仍成立；它们解决的是可执行性，不会自动满足省token要求。另批新题、固定对照、同一实际配置下的来源/读者及真实全成本仍必需。使用更长窗口或不同缓存精度属于受限小模型迁移配置，不冒充无预算限制的原论文精确复现。
